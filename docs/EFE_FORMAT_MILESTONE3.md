# EFE format decoder — milestone 3 evidence

This records the milestone-3 dataset. Later ROM-01/ROM-02 validation and the
runtime-inferred geometry parser are documented in
[FACTORY_EFE_RECONSTRUCTION_V2.md](FACTORY_EFE_RECONSTRUCTION_V2.md).

## Scope and method

This continuation starts at milestone 2 commit `9335bc6`. Analysis compared the
12 private OS 3.53 standalone effect payloads using redacted inventory, and
compared four objects with verified emulator runtime host logs and ES5510
captures. The capture comparison resolves source records using both committed
instruction words and paired GPR values, with contiguous strides and uniqueness
of the resulting layout. Private payloads, raw event logs, captures and their
byte ranges remain outside Git. No external firmware or DSP bytes are included.

## Runtime-verified code layouts

All four verified objects have a common 11-byte region between `FxUcode` and
the first host-correlated record. In mixed layouts, paired records are 3 GPR
bytes followed by 6 instruction bytes (9-byte stride); a three-byte region
separates the paired and instruction-only runs. Instruction-only records have a
6-byte stride. These are source-to-host correlations, not opcode interpretation.

| Effect | Paired | Instruction only | Prefix | Mixed gap | Suffix to FxSize | Evidence |
|---|---:|---:|---:|---:|---:|---|
| 44DDL+CHORUS | 29 | 31 | 11 | 3 | 80 | verified host log + capture |
| 44DDL+CH+REV | 56 | 4 | 11 | 3 | 70 | verified host log + capture |
| 44EQ+REVERB | 26 | 34 | 11 | 3 | 145 | verified host log + capture |
| 44PARAM EQ | 0 | 60 | 11 | — | 122 | verified host log + capture |

The 44DDL+CH+REV source has repeated instruction words; full sequence and host
GPR values disambiguate their locations. The other captures also match all 60
active runtime instructions. `FxSize` is the observed declared end; all four
payloads have additional block padding after it. The parser reports the extent
outside `FxSize` without assigning meaning to it.

## Observed header, extents and checksums

The current evidence supports these observed fields for this object family:

| Offset | Width | Observation | Confidence |
|---:|---:|---|---|
| 10 | 24 bytes, every second byte | printable effect-name characters | observed in 12/12 valid payloads |
| 34 | 4 bytes, big-endian | `FxSize`, declared object end | bounds-checked in 12/12 |
| 38 | 2 bytes, big-endian | `FxUcode`, start of the region under study | bounds-checked in 12/12 |

All 12 effect objects are block-sized (512-byte multiples). The four tested
objects have payload padding after `FxSize`; the remaining eight also have
valid declared bounds, but no runtime layout is claimed for them. No checksum
field or checksum algorithm has been established. SHA-256 values in the private
inventory are integrity identifiers generated by the extraction tool, not
format checksums. There is no demonstrated relationship between header fields
and relocation addresses; `FxUcode` is an object-relative source offset in the
observed comparisons, not a proven load address. Do not treat the 512-byte
container alignment as evidence of an internal checksum or relocation table.

## Suffixes, parameter definitions, and GPR initialization

Suffix sizes are variable across the four decoded layouts (70, 80, 122 and 145
bytes). This proves the suffix is not a fixed-size trailer for these examples.
Its internal record boundaries and meaning are unknown. The prefix, three-byte
gap, and suffix are hashed by the decoder for local differential work, but no
bytes or candidate fields are emitted.

Runtime logs distinguish combined instruction/GPR writes, instruction-only
writes, and GPR-only writes. The four captures include a large number of GPR-only
host events, but those events span initialization and later runtime activity;
they do not by themselves identify parameter-definition records. No parameter
table grammar or generalized scaling curve has been proven. One reversible
ROM-02 control-to-GPR mapping is documented in the later v2 report. A capture's
final GPR image is not treated as pristine file initialization.

## Version differences and loader tracing

The four runtime-correlated examples and the 12-object inventory are OS 3.53
evidence. Existing OS 1.61 runtime/boot traces are not paired with a comparable
set of extracted standalone EFE payloads and effect-selection host logs, so
they do not establish an EFE format version delta. The earlier static report
for OS 3.53 identifies effect-relative update code and service `$801e`, but the
service body and full file-loader path have not been resolved to firmware
addresses. The host logger establishes the writes performed by the executed
emulator, not the exact CPU loader instructions that read each source field.

The other eight effects have no verified standalone-object/runtime correlation
in this dataset. They remain available for private differential analysis but
are not decoded by this milestone's parser. HALL REVERB and ROM-02 are handled
by later source-to-runtime evidence documented in the v2 report; a layout must
not be inferred for any effect solely from instruction count or a six-byte
scan.

## Decoder and extraction tools

`tools/efe_layout.py` and `tools/decode_efe_layout.py` validate segment
geometry supplied from a verified host trace. Start offsets and record counts
must come from a source-to-runtime comparison; prefix, gap and suffix lengths
are then calculated from `FxUcode` and `FxSize`. Example (keep output local):

```sh
python3 tools/decode_efe_layout.py /private/effect.payload.bin \
  --paired-start 813 --paired 86 --instruction-start 1590 \
  --instruction-only 3
```

`tools/compare_asr10_effect_capture.py` is the source/capture/log correlation
tool; `tools/profile_efe_objects.py` inventories object size, declared bounds
and name. Both produce redacted reports. Keep private inputs and reports outside
the repository. Synthetic regression coverage is in `tests/test_efe_layout.py`;
it uses generated bytes only and validates mixed, instruction-only, and bounds
failure cases.

## Follow-up evidence needed

   host writes before claiming their layout.
2. Trace the exact OS loader reads and `$801e` service with an address-resolved
   disassembly or execution trace.
3. Extend the ROM-02 reversible parameter evidence to additional controls and
   determine which GPR-only updates are effect state versus OS/runtime activity.
4. Repeat extraction and runtime correlation on another OS version to establish
   version deltas.
5. Establish file checksum and relocation semantics from loader verification
   and address data, rather than byte-pattern guesses.
